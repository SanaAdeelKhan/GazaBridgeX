# Architecture rules

These are enforced constraints for ANY backend work in this project, not
just performance-review passes — read this file before writing or editing
any model/selector/service/serializer/view, every time (see `CLAUDE.md`).
Every rule below exists because it was found broken in a real app during
the 2026-08 review and had to be fixed after the fact; the point of writing
it down is that a new feature should get it right the first time.

- **O(1) reads.** Dashboard/all-time stats read a stored field off a singleton, never a live `Sum()`/`Count()` over history. Live aggregation only OK when genuinely bounded (month-count trend queries, live snapshot reports like Inventory Valuation). No stored source for a needed number → flag to user, don't silently ship O(n).
- **DRY.** Generalize before duplicating, always follow the Don't repeat yourselft.
- **App shape, every time**: `models.py`, `permissions.py` (`IsAdminOrSuperuser`, admin/superuser-only), `selectors.py` (all reads), `services.py` (all writes, `@transaction.atomic`), `serializers.py`, `views.py` (thin, **generics-based only** — no hand-rolled logic that a generic view already covers), `urls.py`, `admin.py`, `backfill_<app>` command. Never read/write directly in views — go through selectors/services.
- **Pagination always.** Any endpoint whose output is a list gets pagination — use the project's global default `pagination_class`, never `None` and never a custom override.
- **Indexed search always, via `search_q()` only.** ALL text search/filtering goes through `backend.search.search_q(term, *fields)` — never write `icontains` (or any text-match lookup) directly in app code; `backend/search.py` is the single place the lookup lives. Every column `search_q` targets MUST be backed by a pg_trgm GIN expression index — `USING gin (upper(<col>) gin_trgm_ops)` — created in a vendor-guarded migration (`if schema_editor.connection.vendor != "postgresql": return`, so SQLite dev is a no-op; pattern). A plain `db_index`/B-tree CANNOT serve a `%term%` match and is not a substitute. Never ship an unindexed search on a growing table.


- **STRICT: every list/detail endpoint must run in well under 200ms server-side against the real production database (Supabase/any remote Postgres), not just "fast" on local SQLite.** Local SQLite has near-zero per-query latency, so an N+1 that fires 25 extra queries costs a few milliseconds locally and is invisible in dev — the SAME N+1 against a real network-hosted Postgres costs roughly 100ms PER QUERY (measured, not estimated: `aws-*.pooler.supabase.com` from this project's own dev machine), so 25 extra queries is ~2.5 seconds of pure network round-trip time, and 50 extra queries is ~5 seconds. "It feels fine when I test it" is not verification — count the actual queries (`django.db.connection.queries` with `DEBUG=True`, or a `CaptureQueriesContext` test) before calling any endpoint done. A paginated list endpoint (25 rows) has no excuse to run more than a small, fixed number of queries (typically 2–4: count + page + at most one or two prefetches) — if it's more than that, it's an N+1, not "the database being slow."
- **STRICT: a serializer's relations have a blast radius — changing one serializer can silently break a DIFFERENT selector in a different app.** **The rule: whenever you add a field to a serializer that requires a new relation (FK, reverse FK, OneToOne), grep every place that serializer is used — both views that serialize it directly AND every other serializer that nests it — and add the matching `select_related`/`prefetch_related` to every queryset that feeds ANY of them, not just the one you're directly editing.** Don't consider the change done until you've traced the full nesting graph.
- **Convert a check-then-act uniqueness/protection violation into a clean 400, don't let it crash.** Any `if Model.objects.filter(...).exists(): raise ValidationError(...)` immediately followed by `.create()` has a race window where the DB's own constraint (`UniqueConstraint`, `on_delete=PROTECT`) fires instead — wrap the create/delete in a savepoint, catch `IntegrityError`/`ProtectedError`, and re-raise the SAME `ValidationError` the pre-check would have given. The success path is untouched; only the crash-on-race path becomes a normal 400.
